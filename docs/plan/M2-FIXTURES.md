## What each fixture describes

The sentence below each name is the fixture's own `about` field, quoted, so
the page cannot describe a fixture differently from the file it came from.

**`disk-full-for-eleven-minutes`** — C: has been 95 % full (25 GiB free of 500) for eleven minutes, so it is past the ten-minute window.

**`disk-cleared-before-the-window`** — C: was 95 % full for eight minutes, then something was deleted and it sat at 60 % for three: the window that matters is clean, so nothing is said.

**`disk-ninety-eight-is-critical`** — C: at 98 % (10 GiB free of 500) is the same rule at a severity that says data loss is plausible.

**`disk-network-and-unreadable`** — A network share at 99 % is not this machine's problem, and a volume Windows refuses to describe is unknown, not empty - neither may produce a finding.

**`memory-tight-for-three-minutes`** — 13.6 of 16 GiB used (95 %) for three minutes, which outlasts the two-minute window.

**`memory-dipped-inside-the-window`** — Three minutes at 95 % followed by a minute at 70 %: the last two minutes contain the dip, so the pressure is not sustained and nothing is said.

**`uptime-twenty-days`** — Twenty days without a restart is worth a sentence, not an alarm.

**`uptime-one-hour`** — An hour since boot is a normal machine; a long uptime only gets mentioned after a fortnight.

**`memory-commit-tight-for-six-minutes`** — 22.3 of 24 GiB of commit in use (93 %) for six minutes, with RAM at half: the machine is out of promises, not out of memory, which outlasts the five-minute window.

**`memory-commit-two-minutes-is-not-five`** — Commit climbs to 93 % only two minutes before the last sample. The number is above the threshold and the window is not - a machine that has just started paging in hard should not be reported as one that has been stuck there.

**`memory-commit-eighty-nine-is-not-ninety`** — Commit sits at 89.5 % for six minutes: adjacent to the threshold, never over it, and held for longer than the window. The cheap near-miss - a machine nowhere near the number - would not catch an off-by-one.

**`runaway-cpu-holds-a-core`** — render.exe (pid 4242) uses 96 % of a core for eleven minutes while the machine sits at 20 %: one process that never comes down, which outlasts the ten-minute window.

**`runaway-just-under-for-twelve-minutes`** — The same process at 79 % of a core for twelve minutes: adjacent to the threshold, held well past the window, and never over it. A rule with an off-by-one on 80 would fire here.

**`runaway-pid-reused-every-five-minutes`** — Pid 4242 is busy at 96 % for five minutes, exits, and the pid is handed to a new process that is also busy for five minutes. Windows does this all day. Two five-minute processes are not one ten-minute process, and the creation stamp is the only thing that says so.

**`memory-growth-leaks-four-hundred`** — sync.exe (pid 5150) holds 300 MiB for fifteen minutes, then 700 MiB for sixteen more: 400 MiB gained over half an hour and none of it given back.

**`memory-growth-just-under`** — The same shape, 255 MiB instead of 400: a file being loaded and kept, which is what a cache looks like. One megabyte under the threshold, held for the whole window.

**`memory-growth-pid-reused`** — Pid 5150 holds 300 MiB for fifteen minutes, exits, and the pid is handed to a process that starts at 900 MiB. Comparing the two would report 600 MiB of growth in a process that never grew at all - which is why the rule asks for the same creation stamp at both ends.

**`disk-slow-transfers-for-eleven-minutes`** — Every disk transfer averages 180 ms for eleven minutes while the CPU sits at 20 %: the disk is the queue, which outlasts the ten-minute window.

**`disk-slow-transfers-just-under`** — 99 ms per transfer for twelve minutes: one millisecond under the line, held well past the window. A mechanical disk doing a backup looks exactly like this and is not being reported as failing.

**`disk-slow-transfers-break-in-the-middle`** — Six minutes of 180 ms transfers, one minute of idle disk, five more minutes of 180 ms. The window is not held for its whole length, so this is a burst - and a rule that averaged instead of requiring the whole window would call it a sustained fault.

**`pages-input-sustained`** — 150 hard faults a second for six minutes with RAM at half: memory is being written out and fetched back, so the disk is standing in for it.

**`pages-input-just-under`** — 95 hard faults a second for twelve minutes: adjacent to the line, held well past the window, and never over it. A machine doing real work, not one that has run out of memory.

**`pages-input-broken-in-the-middle`** — Three minutes of hard faults, one minute of quiet, three more minutes of hard faults: a program starting and settling, not a machine that has run out of memory. The window is not held for its whole length.

**`cpu-sustained-for-eleven-minutes`** — Every core at about 92 % for eleven minutes: a machine using all of itself, which is a render or a build. The whole-machine rule fires and the pinned-core rule stays quiet — a machine busy everywhere is not one program on one thread.

**`cpu-just-under-for-twelve-minutes`** — 89 % for twelve minutes: one point under the line, held well past the window. A machine near its ceiling is what a build looks like, and neither CPU rule has anything to say about it.

**`cpu-busy-then-idle-then-busy`** — Six minutes at 92 %, two minutes at 25 %, five more at 92 %: one build finished and another started. The machine was busy on both sides of the gap and never for ten unbroken minutes, so sustained stays quiet.

**`one-core-pinned-for-eleven-minutes`** — Core 0 at 98 % for eleven minutes while the machine sits at 22 %: one program doing all of its work on a single thread, on a machine with seven cores going spare. The overview reads calm and the program will take as long as one thread takes.

**`one-core-just-under-the-line`** — Core 0 at 94 % for twelve minutes: one point under the pin threshold and held well past the window. A program that is merely busy on one thread is not a pinned core, and a rule that said so would fire on every browser tab.

**`disk-filling-fast-for-forty-minutes`** — C: goes from 60 % to 62 % full in twenty minutes on a half-terabyte volume: ten gigabytes written, and none of it freed. The half-hour window is spanned, so the rate is a measurement rather than a guess.

**`disk-filling-just-under`** — The same half-terabyte volume loses 4.5 gigabytes across forty minutes: under the five-gigabyte line, and held well past the window. A large file being copied is not a disk filling up.

**`disk-freed-again-inside-the-window`** — Ten gigabytes go, five minutes later they are back, and the volume ends the half hour exactly where it started. Comparing the ends of the window rather than the peak inside it is what keeps this quiet.

**`gpu-vram-over-the-line-for-six-minutes`** — One discrete adapter uses 7865 of its 8192 MiB of dedicated memory - 96 % - for six minutes. Past the five-minute window, so it is the driver moving data into system memory rather than one level loading.

**`gpu-just-under-the-line`** — The same adapter at 7770 of 8192 MiB - 94.8 % - held for twelve minutes. One percent under, held long past the window: the threshold is what keeps this quiet rather than the timing.

**`integrated-gpu-reports-no-limit`** — An integrated adapter: 512 MiB in use, no dedicated memory of its own, so the counter reports a limit of 0. There is no percentage of nothing, and the rule says nothing instead of 100 %.

## What these fixtures do not prove

They are recipes, not captures. Each segment says "ten minutes at 92 %" and the
harness expands it to a 1 Hz sample series, which is what the collector *would*
have produced — but no Windows counter produced it. Nothing here has been
compared with Task Manager, and nothing here has been through a compiler.

Two things follow, both recorded in [`M2-VERIFY.md`](M2-VERIFY.md):

- The fixture count is not coverage. A rule can pass every fixture and still be
  wrong about a real machine, which is what the five-machine review is for.
- `gpu.vram_pressure` cannot be provoked on Windows 7 at all, because the counter
  set does not exist there. `integrated-gpu-reports-no-limit` is as close as the
  old machine gets: it proves the silence, not the firing.
