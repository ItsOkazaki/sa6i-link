# Sa6i Clean inside Sa6i Link: integration work

## Requested behavior

A button in Sa6i Link switches the **same main window** to the Sa6i Clean layout. The current working installation and published releases must remain unchanged. The separate Sa6i Clean candidate remains available as a fallback. This is not a request to launch a separate visible app window.

## Current source status

**Latest Windows 7 feedback:** the user reported that the header-clearance preview looks good and that Back/reopen, resize and maximize work. They initially reported slow reopening; with the later reopen-speed update, they confirmed Clean opened in the same UI and reopening felt much faster. These are observations on that setup, not cleanup safety or full compatibility. The 40-logical-pixel strip is a workaround; the underlying compositor discrepancy is still not understood. The full cleaner is not restricted or sandboxed and can perform destructive actions. The previous build reports below describe earlier stages, not the latest visual result.

An explicitly guarded Windows experiment now wires a Sa6i Clean entry, alternate layout, native adapter and controlled-close coordination into the checkout's app source. Known main-window prompts and toasts request temporary suspension of the cleaner view and native child; native hiding is asynchronous and not verified on Windows. GitHub Actions successfully built and staged the guarded Windows x64 source with both official Qt 6.12 and a pinned third-party Qt 6.8.3 Windows 7 backport. Earlier builds were not validated as deliverables or release candidates; a later, separately bundled preview has since received the limited Windows 7 visual feedback described above. The Qt backport and its licensing still require review. Isolated Qt tests use a simulated parent window and fake Win32/cryptography. The published executable and the user's installation are untouched. See `QT-HOST-PLAN.md` for the build/runtime guards, unresolved safety issues and validation gaps.

The opt-in Windows source build now requires an explicit absolute `--data-dir` and contains source-level guards disabling update checks, staging and installation, plus setup, removal and privileged helper modes. It also suppresses Windows toast registration/history, Jump List updates, phone-storage sync-root handling and Windows global hotkey registration (including settings changes). These guards are unverified in the actual app; networking, clipboard monitoring, other OS integrations and independently scheduled tasks remain outside them. The experimental backend creates a fresh temporary directory per launch and supplies it to Electron via `--user-data-dir`; it aborts if creation fails. The latest path is available as the adapter's `testProfile` property. Directories persist after exit and even if launch fails, and may contain sensitive data. This differs from the earlier standalone probe. Source inspection suggests the flag affects settings and the single-instance lock, but actual behavior on Windows is unverified. It is **not a sandbox**: the cleaner can access other user and system paths. Use only a disposable test environment with backups; do not assume a fresh profile protects an existing installation or its data.

## Findings

- Sa6i Link source in this checkout uses Qt Quick/QML, with pages switched by `desktop/app/qml/MainWindow.qml` through a QML `Loader`. That loader currently requires a ready/paired state. Its working Windows binary is a patched build whose exact source/build provenance is not established; a build from this checkout is not automatically equivalent to the user's tested executable.
- The user supplied `Sa6i.Link.zip`, SHA-256 `18e66fe82dc1fad747e192a2bb0aef3c8fdac8d2398f974a73f4853d16d89d12`, which matches the published Windows ZIP. It contains the packaged executables, Qt runtime, plugins and third-party QML, not a matching developer source project. After normalizing the top-level folder, its 1,215 files all match the corresponding files in the previously tested artwork candidate; the latter additionally has `START-HERE.txt` and `THIRD-PARTY-NOTICES.txt`. The published ZIP does include `LICENSE` and `LICENSES`, but omits that separate third-party notices file. Preserve/review the notices in future packages; do not silently alter the published asset. `Sa6i Link App.exe` hashes to `c168bfcd6b51d3528ea78a6c0d135c9d101b9e839c6785facb5f38f5d109daf5` and is not byte-identical to the separately preserved v8 baseline executable.
- A read-only, hash-locked inspection recovered the compressed main-window QML resource from this exact executable. Its normalized lines closely resemble the checkout's QML, but include binary-patched branding and a Windows 11 frame workaround. This is one UI resource, not the whole project. The executable also contains the earlier cache-fallback marker. The resource has limited reserved compressed space; a QML change alone cannot implement the native cross-process host, and no integrated build exists yet.
- The supplied Sa6i Clean is a packaged Electron app. Its renderer expects `window.cleanly`, populated by `dist-electron/preload.cjs`, and communicates with its Electron main process for scanning, cleaning, operating system operations, settings and services. The React bundle on its own is **not** a functional cleaner. It has a demo fallback when `window.cleanly` is absent; showing that fallback as if it were real would be misleading.
- The repository's Qt build does not currently configure Qt WebEngine or a Cleanly bridge. Embedding the renderer in the same Qt window needs a compatible rendering engine and a secure, implemented bridge to the cleaner backend, or an independently validated alternative. Qt WebEngine is only one possible approach: availability and operation on Windows 7 with VxKex must be investigated, not assumed. A plain QML loader cannot load the Electron interface.
- Reparenting a separately running Electron window using native Windows APIs is another possible experiment, but can fail due to cross-process DPI, window lifecycle, focus, privilege boundaries and VxKex. It should not be grafted into the working executable without a disposable test and a safe rollback.

## Work in this directory

`renderer-bridge.mjs` is an isolated adapter prototype matching the 24 method names and `onProgress` exposed by the supplied Cleanly preload. Its transport is injected; it has **no cleaner implementation, no Qt integration, and no access to files**. `test-renderer-bridge.mjs` verifies the adapter using an in-memory mock. Run:

```sh
node --test sa6i/clean/test-renderer-bridge.mjs
```

This prototype is not wired into either application, is not a finished integration, and does not establish that the actual Qt/Electron bridge is viable. Method forwarding is not authorization: any real host must independently authenticate the renderer and validate and authorize each method, argument and event. In particular, no generic arbitrary command or file access may be exposed to untrusted content. Navigation, external links, secrets, IPC endpoints and privilege boundaries need explicit review.

`inspect_link_window.py` extracts and verifies the known compressed QML window resource **without modifying the ZIP or executable**. It refuses unknown inputs and an existing output file. Example: `python3 sa6i/clean/inspect_link_window.py google_drive/Sa6i.Link.zip /tmp/sa6i-mainwindow.qml`. The recovered QML can inform a separately tested candidate; it does not provide the missing host or full source.

## Standalone native host probe

`host_probe.c` is a separate, rudimentary Windows Win32 window with Home and Sa6i Clean buttons. Home is a placeholder, not Sa6i Link. Clean launches the adjacent **restricted** test cleaner and attempts to parent its window inside the host. The user reports the header-adjusted cleaner appeared inside the test host on their Windows 7 + VxKex setup; opening the cleaner directly showed its own separate window, as expected. The user also reports that Home/Clean switching and resizing worked in the probe. This is encouraging evidence of embedding on that setup, but **is not the requested integration**, and is not merged into Sa6i Link. DPI changes, focus, more navigation cases, failure handling and teardown still need testing. Failure can leave a separate cleaner window running. It does not terminate an undiscovered process.

The `--restricted` builder option uses a separate app name and blocks 12 selected destructive, settings and network Electron IPC routes, including cleanup and uninstall. The bundled app may still read files, write runtime files, and have other behaviors: this is not a security audit. `verify_restricted_main.mjs` checks the exact generated main file hash before evaluating the dispatch table, then verifies those 12 handlers reject; these are not end-to-end tests. The host verifies exact hashes of that one restricted executable and ASAR before launching, to avoid accidentally hosting the unrestricted app; this is not a defense against malicious file replacement. The exact app data path is not verified on Windows.

The probe was cross-compiled with Zig 0.13.0 for Windows x64, linked only to USER32, KERNEL32 and ADVAPI32, with a GUI subsystem and declared OS version 6.0; this does not prove Windows 7 compatibility. A user ran the diagnostic host and reported Windows CreateProcess error 193 (not a valid Win32 application) before the cleaner launched, even with VxKex enabled for that test cleaner. The restricted cleaner is a valid x64 PE whose header declares OS and subsystem version 10.0. In i486/VxKex source `KexDll/cpiwbypa.c`, its bypass for the subsystem-version check patches the *calling process*'s CreateProcessInternalW; `KexDll/initapc.c` applies it on VxKex initialization. The host is a separate calling process, so enabling VxKex for the diagnostic host as well is a plausible experiment, not a confirmed solution. See https://github.com/i486/VxKex/blob/main/KexDll/cpiwbypa.c and https://github.com/i486/VxKex/blob/main/KexDll/initapc.c. VxKex versions and settings can differ. The prior independent cleaner worked for this user with VxKex, but does not verify this build. Do not perform cleanup tests on a production machine. Any actual integration will still need to attach the cleaner safely to the existing Qt/QML window and preserve the user's working version.

### Header overlap follow-up

The user confirmed the updated full-cleaner preview opens, but its screenshot still shows the native cleaner covering the lower part of the Back header. The screenshot does not identify the root cause: DPI behavior and cross-process positioning are possibilities, not established facts. The host now creates a same-process native clipping container at the Qt viewport and reparents the cleaner into it, so the foreign child cannot paint or receive input outside that container. Hiding the container occurs on the host thread before the asynchronous child hide; the tracked process is still closed and reaped before the container is destroyed. Native Windows smoke `44802136338` passed with a deliberately misplaced inert child; full-window smoke `44805274715` passed with inert native and Electron children, checking the Back area and container geometry. The Win7 backport build `44802136514` produced desktop SHA-256 `9f6ed53b2b62bb07a930e4216222400668ba2fe862e95430950dfef8aee2d30b`. A small update containing that desktop and its matching camera DLL is intended only for the previous UI preview. These tests are not a substitute for actual Windows 7/VxKex validation; viewport mapping, compositor behavior and real Electron rendering remain unverified there.

### Windows 7 header probe

After the user confirmed VxKex was enabled on both test cleaner and diagnostic host but error 193 remained, `make_win7_header_probe.c` and the `WIN7_HEADER_PROBE` build of `host_probe.c` were cross-compiled as a separate experiment. The creator verifies the exact restricted cleaner hash, creates a new file without overwriting, and changes only its OS/subsystem header fields from 10.0 to 6.1. The probe host allows only that exact modified hash and the existing restricted ASAR. The user first reported a missing GetAddrInfoExCancel entry point in WS2_32.dll. Lowering header versions does not implement missing APIs. The new filename requires separate VxKex settings; the user initially reported that after Apply the checkbox was off again before launching, with no Windows prompt. After being directed to use KexCfg as administrator for the new test executable, the user reported it opened within the test host; direct launch showed a separate window. The user also confirmed Home/Clean switching and resizing worked. Other behaviors have not been verified. i486/VxKex source indicates configuration is written to Image File Execution Options through a privileged helper, which can fail; no prompt is also expected in some versions using a scheduled task. The user's actual VxKex variant/version and original failure cause are unknown. i486/VxKex source has a `ws2_32` redirect to `kxnet` and an implementation of the function, but the user's VxKex variant/version and its activation path are not yet known; this is not evidence that their installation provides or loaded it. A unit test verifies the byte change and hash using the local fixture. Never apply these changes to the user's working release.

### Lifecycle model (not connected)

`host_lifecycle.c` and `test_host_lifecycle.c` model navigation, discovery failure and process exit without Windows or Qt calls. Unlike the original probe, the model keeps tracking a known process after timeout, failed embed or child-window loss, preventing a second launch while the first may remain alive. It requests a graceful close only for a known embedded window, and does not terminate an unknown process. It deliberately remains in `HOST_CLOSING` until exit is observed; a bounded close UX and safe strategy for a stuck process still need design. This is a model, not process ownership enforcement, a working implementation, or evidence of safe behavior. Test with:

```sh
cc -std=c11 -Wall -Wextra -Werror -pedantic sa6i/clean/host_lifecycle.c sa6i/clean/test_host_lifecycle.c -o /tmp/sa6i-host-lifecycle-test
/tmp/sa6i-host-lifecycle-test
```

The source checkout's `--data-dir` supports isolated core data and influences its single-instance key, but other global Windows integration paths can still have side effects, and the exact published binary is not proven equivalent. Do not launch a copied release assuming this flag isolates everything.

## Remaining work before an integrated candidate

1. Obtain or establish a reproducible source/build matching the user's working Windows Sa6i Link, or clearly accept and test a separate source-built candidate. Do not overwrite the working build.
2. Build and review the guarded single-window host in Sa6i Link; the standalone probe demonstrated basic embedding, switching and resizing on the user's Windows 7 + VxKex setup, but not actual app integration. Verify profile behavior, focus, close-to-tray, failures and rendering on disposable machines without triggering deletion. Avoid exposing a fake Demo mode as real data. See `QT-HOST-PLAN.md`.
3. Review lifecycle and renderer security, and preserve attribution and validate third-party licensing for any chosen approach. The current experiment hosts the restricted Electron app and does not use the renderer bridge prototype; if that bridge is pursued instead, implement and authenticate its actual transport and per-method permissions. Address distribution terms for the integrated combination.
4. Review cleanup behavior and test in an isolated environment with synthetic data and backups. Some operations permanently delete files; see `SAFETY-REVIEW.md`. The full fixture currently exposes destructive features and does not enforce this intended restriction; safeguards remain to be designed and verified before release.
5. Produce a separately named package, check data isolation, and validate on Windows 7 with VxKex as well as Windows 10/11 before considering distribution. The independently tested first cleaner preview does not establish that the integrated app or later preview works.

## Full-cleaner integration build in progress

A separate experimental build can now be selected with **both** `SA6I_CLEAN_EXPERIMENT=1` and `SA6I_CLEAN_FULL_FIXTURE=1`. This variant keeps the guarded application startup and only accepts the exact full cleaner fixture; ordinary builds and the restricted experiment are unchanged. Unlike the restricted fixture, this full cleaner includes destructive cleanup, uninstallation, startup-management and network operations. It is **not a sandbox** and is not ready for production use.

To prepare the current exact cleaner, build the non-restricted branded cleaner with `build_candidate.py`, then run `prepare_integrated_ui.py <branded-folder> <new-folder>` followed by `prepare_full_integration.py <new-folder>`. The first step checks the inspected input hashes, creates a separate copy, changes the Electron window to frameless and removes the native-overlay theme update, and updates the executable's ASAR integrity resource. It leaves the renderer's own scan-status bar and cleanup code intact. The second verifies the new pinned hashes and changes only the PE operating-system and subsystem version fields from 10.0 to 6.1 in a new `Sa6i Clean Integration.exe`. Its SHA-256 is `435923fe5a7404feef6bdf242b444dda5def1a05d68a720038e41294086dbb4e`; the modified ASAR SHA-256 is `62b7546a12ddac85b6fc506b0fb151acd15944ce3a809f9f4c8390965ef1080a`. The next experimental version additionally runs `prepare_themed_fixture.py <full-cleaner-folder> <new-themed-folder>`. ### Approved quit fix and rebuilt preview

The native experimental window was intercepting every close event. Qt 6.8.3 handles application quit by closing top-level windows and cancels quit when a window rejects its close event, so the interceptor could reject the close initiated by Qt itself. Commit `bb98f13` defers an approved quit until the original close event has unwound, rechecks cleaner ownership, then allows the native close only during the guarded synchronous quit call; a tracked process or pending launch still blocks quit. The in-memory QML lifecycle tests pass, including ownership changes before the deferred call. In [Windows CI run 44757980827](https://github.com/ItsOkazaki/sa6i-link/actions/runs/44757980827), the rebuilt backport-based desktop passed a software-rendered `--ui-check` startup and shutdown with **no cleaner launched**. The full cleaner was assembled only after building: the separately stored preview remains experimental and must not replace a working installation or be published.

### Reopen speed investigation

The Back action keeps the tracked cleaner process alive when it remains healthy; it hides the native child rather than deliberately launching the cleaner again. Previously, each visible viewport synchronization applied geometry using the old selection and then applied selection separately. On reopen this could queue a hide followed by a show; during steady display it issued two placements per synchronization. The new source combines verified geometry and selection into one native placement while retaining the regular reassertion, clipping parent, failure handling and process-ownership checks. A simulation asserts one placement and no extra hide on reopen, plus invalid-geometry and close behavior. This reduces redundant requests. The user subsequently reported that reopening felt much faster on their Windows 7 setup, but there is no measured benchmark and the original cause remains unconfirmed. Chromium rendering, scheduling, storage and hardware may also affect responsiveness.

The synthetic Windows smoke now logs diagnostic time from posted reopen click to native-window visibility and, when observable, an inert green Electron pixel. These are coarse 100 ms-polled metrics, not measurements of the real cleaner's usable UI, and the green-pixel timing is inconclusive if the screen did not clear while hidden. Windows 7/VxKex and the real cleaner still require separate measurement; do not treat this performance change as release validation.

The combined-viewport change passed [hosted Windows synthetic build/smoke run 44931201549](https://github.com/ItsOkazaki/sa6i-link/actions/runs/44931201549), the [Win32/Qt inert-host run 44931201529](https://github.com/ItsOkazaki/sa6i-link/actions/runs/44931201529), and [simulated QML/native run 44931201538](https://github.com/ItsOkazaki/sa6i-link/actions/runs/44931201538), all at commit `81f06d2`.
