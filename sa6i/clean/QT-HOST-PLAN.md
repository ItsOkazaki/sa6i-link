# Sa6i Clean host integration: Qt design notes

Status: **source-level experimental integration, not built or tested as Sa6i Link on Windows and not suitable for release**. The checkout now has guarded wiring from MainWindow's cleaner entry/layout to the adapter and from App's controlled close paths to the close coordinator. The default build has no cleaner backend; the Windows-only experiment requires build-time `SA6I_CLEAN_EXPERIMENT=1`, an explicit absolute `--data-dir <directory>`, and `--sa6i-clean-test-dir=<absolute directory>` to expose the cleaner entry. No integrated executable or package has been produced. The user reports only the earlier standalone restricted Windows 7 probe embeds the cleaner, switches Home/Clean and resizes. That result does not validate this source wiring, close-to-tray, DPI, focus, security or a Sa6i Link build.

`CleanEntry.qml` is a navigation button and `CleanView.qml` a view with a Back signal, status text and native-host viewport. The standalone copies remain under `sa6i/clean/`; guarded app copies are under `desktop/app/qml/components/`. `Sa6iCleanIntegration.qml` coordinates them without changing `AppController.currentPage`, supports entry before pairing, starts only the pinned probe through the adapter and hides the child on Back. `test_clean_view.py` exercises the standalone components offscreen. `test_adapter_gate.py` additionally loads the actual app integration QML with a simulated window, the Qt adapter and fake Win32 backend, exercising entry, Back, close and cancellation. This is not the real MainWindow, process or Win32 integration. The sandbox run used software rendering and temporary test-only graphics/DBus stubs that abort if invoked; it was not a Windows or GPU test.

`native_embed.c` / `.h` implement an experimental host API using Win32: exact restricted fixture hash checks, one launched process at a time, attach, resize, hide/show, timeout/error tracking, graceful close requests and cancellation of a pending shell close. After verifying the fixture, each launch creates a new `Sa6i-Clean-HostTest-<pid>-<n>` directory under the current user's temporary directory and passes it as a separately quoted `--user-data-dir` argument; it fails closed if the directory cannot be created, and never deletes it automatically. The adapter exposes the most recent directory as `testProfile` after worker handoff (a later attempt or rebind may replace that value). These directories can contain sensitive test data and accumulate, including after failed starts. This is intended to separate Electron profile/settings and instance lock, **not** to sandbox filesystem, network, shell, OS-profile or registry access; the cleaner may still read or write outside that directory. The profile switch and its effects are not verified on Windows. It expects a top-level parent HWND and already-mapped client coordinates; it is exposed through the experimental Qt adapter. It compiles for Windows x64 with Zig, and `tests/test_native_embed.c` simulates Win32 calls for normal, timeout, launch/attach failure, lost-window, close failure and cancellation paths. The simulation uses fake Win32/cryptography and is **not** an actual Windows, hash, DPI, focus, process or security test. Hash tests elsewhere check the known files separately. The API can stay in CLOSING indefinitely if a process refuses to exit, and cross-process async window operations still need careful validation. Its file handles limit ordinary concurrent replacement while launching but are not a defense against malicious filesystem races. Never use this code in a release without Windows testing and review.

Run the simulation with:

```sh
cc -std=c11 -Wall -Wextra -Werror -pedantic -I sa6i/clean/tests/win32 sa6i/clean/tests/test_native_embed.c -o /tmp/sa6i-native-embed-test
/tmp/sa6i-native-embed-test
```

`qt_embed_adapter.{h,cpp}` is an experimental QObject wrapper around the C backend. It exposes QML-callable close, cancel, polling, geometry, selection and launch methods; only a C++ owner can bind the actual parent HWND. It schedules verification and launch on a worker using an isolated host copy and transfers ownership back to the GUI thread after the worker finishes. `start` returning true means the operation was scheduled, not that launch succeeded. `processTracked` includes unresolved launches and `launchPending` distinguishes that phase; a pending close waits for handoff and process exit, while cancellation retains ownership. Geometry/selection changes made during verification are reapplied at handoff. Its own timer continues tracking the process after close cancellation. It refuses rebinding while a process or launch is tracked and requires explicit rebind after a completed close. Mutating methods reject calls from outside the object's owning thread; the owner must keep it on the GUI thread. It cannot itself prevent its owner from being deleted or the HWND from being destroyed; a warning in its destructor is not protection. If unexpectedly destroyed during launch, it waits for the worker, potentially blocking, and cannot safely contain a process already spawned. Thread-creation failure is reported as a generic resource error, and a worker stalled indefinitely remains pending. This worker design remains experimental and needs review and real Windows tests. It does not itself handle viewport mapping or window teardown; its temporary profile does not isolate all application data.

`tests/test_qt_embed_adapter.sh` builds the adapter against QtCore and runs it with the **real C backend compiled against fake Win32 and fake cryptography**, plus a non-Windows stub test. With `RUN_QML_TEST=1`, it also loads a test-only shared library into PySide and exercises the QML integration and close gate through the adapter into the simulated backend (`test_adapter_gate.py`). It runs `test_app_close_wiring.py`, which extracts the actual `App.qml` close functions and controller quit handler into a QML harness with mock window/loader objects and checks normal tray, controller quit, pending process, deferred recheck, reactivation and teardown refusal. A generation counter prevents a queued tray teardown from undoing a later `showMain` activation. If reactivation happens before tray approval, it asks the gate to cancel that tray action, while preserving a pending quit; if approval already happened but teardown has not, it re-arms the cleaner entry only after the tracked process has exited. A previously posted `WM_CLOSE` is not revoked. `test_tray_reactivation.py` exercises the actual integration component and extracted App/MainWindow functions with a QML fake backend, covering both timings, failed cancellation, quit and a new launch; it is not a real process or Windows test. Additional tests connect the extracted App functions through the actual integration component to the C++ adapter and fake Win32 backend. They cover reactivation before tray approval with a still-tracked process, reactivation during a blocked launch, late exit after cancellation, reactivation after approval followed by parent rebind and a fresh launch, preservation of a pending quit, and an immediate second tray close. The parent rebind is a test hook calling the real adapter binding method with a simulated HWND; it is not the actual NativeWindow implementation. These tests substitute preferences and do not instantiate the complete real `App.qml`/`MainWindow.qml` or native window. For the local run, QtCore headers and moc came from a sandbox-built QtBase 6.8.3 source tree, and the QML test used the PySide6 6.8.3 runtime with temporary offscreen graphics/DBus shims. These were separate builds with potentially different build configurations and are for isolated testing only, not a supported SDK or release artifact. The QtBase install step was incomplete, though the build-tree Core and moc targets were usable. The simulation can deliberately block fake file reads, exercising GUI responsiveness, closing/cancellation during launch, handoff, launch failure and independent polling. A close requested during launch or discovery clears the desired selection before polling or handoff, continues discovering within the existing timeout, requests that a discovered child be hidden, and posts a single close request. Regression tests exercise a window appearing exactly before the close's discovery poll, a blocked launch with a selected view, and the QML Keep open path restoring selection after cancellation. Discovery timeout or attachment failure retains the process and requires manual resolution; cancel keeps tracking it. The cleaner initially creates a visible top-level window, so it can be visible before discovery/attachment, and asynchronous hiding and close messages are not guaranteed to complete before the QML prompt appears. The fake tests cover these branches but do not establish real cross-process ordering. No test used actual Windows, Win32, real hashing, process creation or Sa6i Link. The fake tests don't establish ABI compatibility for a production build.

`viewport_geometry.c` is a Qt-independent mapping helper now called by the guarded `NativeWindow::sa6iSyncCleanViewport`. It accepts the four `mapToScene()` corners, an explicit DPR and a client size, rejects unsupported transforms and non-finite values, and inward-rounds and clips the result to the client rectangle. The guarded window code also checks visible, opaque ancestors and whether the viewport fits within clipping ancestors. `tests/test_viewport_geometry.c` tests the helper, not the new Qt/Win32 caller. Qt DPR versus Win32 DPI virtualization and asynchronous native ordering remain unverified. They are integration prerequisites.

The experimental MainWindow wiring now reports its known pairing, ringing, remote-input, PC-mirror and continuity prompts, doctor sheet, command palette and toast to `Sa6iCleanIntegration`. While any is visible, it requests hiding the native child and hides the cleaner layout/entry so the existing overlay can be reached; the cleaner stays tracked and can reappear after the overlay closes. Sheet visibility includes closing fades. This also intentionally suspends the cleaner for toasts. Tests simulate overlay interaction, an overlay during blocked launch, and cancellation while an overlay is open; an additional test evaluates the actual MainWindow binding expression using stand-in items. They do **not** instantiate the real MainWindow, enumerate every nested popup, or test a real HWND. The backend now reports a rejected `ShowWindowAsync` request instead of reporting success, and the integration records `hideRequestFailed`, logs a warning and retries while it remains hidden by the QML state. A successful return only means that Windows accepted a request, not that the child is actually hidden. Cross-process hiding is asynchronous and cannot guarantee the child is gone before a sensitive prompt appears; a warning itself may also be obscured. The fake tests cover failure, tracking and retry, not actual Win32 behavior. Reliable ordering, all other dialogs, focus and Windows behavior must be reviewed and tested before any release.

## Checkout build integration observations

- `desktop/app/build.rs` uses `cxx_qt_build::CxxQtBuilder` to register the `app.nectarlink` QML module and compile `cpp/native_window.h` and `.cpp`. Source wiring adds the four QML components, generates a configuration header, and adds the native adapter/backend/geometry sources and `advapi32` only for the explicitly opted-in Windows build. None of these changes has been validated with a full Cargo/Qt build, including ordinary non-Windows builds.
- `tests/check_windows_cpp_objects.sh` provides a narrower cross-compilation check: with supplied Zig, moc, Qt headers and cxx headers it compiles the actual Windows `native_window.cpp` in both modes, the adapter, C backend and geometry (as C++), plus generated moc objects. It checks that the ordinary window object has no adapter/viewport references and the experimental one does. Locally this passed with Zig 0.13, Qt 6.8.3 source headers assembled using a **Linux-configured** QtBase tree and hand-written temporary Qt Declarative feature/export headers, plus cxx 1.0.202. These are test-only headers, not a Windows SDK; the Qt moc was a Linux build and `WINVER=0x0a00` was supplied for the MinGW headers. The objects were not linked or run, and this does not verify CxxQtBuilder, Windows Qt configuration, ABI or the application. The same native window source also passed a Linux ordinary-mode C++ syntax check with the temporary headers. A real supported Windows Qt/Cargo build is still required.
- The Windows-target window objects expose imports of `GetDpiForWindow` and `GetSystemMetricsForDpi` from existing non-experiment code; these are not native Windows 7 APIs. The current i486/VxKex source exports implementations of both, but the user's VxKex variant, activation and actual app behavior are not established. Even with those functions available, other Qt/app dependencies may prevent launch; this is not evidence of Windows 7 compatibility.
- A potential future research input is [xanasoft's Qt 6.8.3 Windows 7 build](https://github.com/xanasoft/qt-builds/releases/tag/v6.8.3-ssl-lgpl), which describes its basis as the [crystalidea Qt 6 Windows 7 backport](https://github.com/crystalidea/qt6windows7). These are third-party builds/patches, not used here or endorsed as safe; review provenance, exact source/build correspondence and license obligations before use. The checkout's workflows specify Qt **6.12.0**, so a 6.8.3 replacement may lack APIs or QML modules this application needs. A patched Qt also does not resolve the app's own imports, Electron/VxKex dependencies or this integration's lifecycle and DPI risks. The asset was not downloaded or tested; there is no evidence it builds or runs this app.

For the cross-object check, provide locally prepared inputs, for example:

```sh
SA6I_ZIG=/path/to/zig SA6I_MOC=/path/to/moc \
SA6I_QT_INCLUDE_DIRS=/path/to/qt/include:/path/to/qtdeclarative/include \
SA6I_CXX_INCLUDE_DIR=/path/to/include-containing-rust-cxx-h \
bash sa6i/clean/tests/check_windows_cpp_objects.sh
```

Use matching, appropriate SDK headers for meaningful build validation; merely passing this check with assembled test headers is not a substitute for the actual app build.

- `MainWindow.qml` keeps `page` synchronized with `AppController.currentPage`. The experiment uses its own `cleanOpen` state and puts its entry in the title strip so it is potentially available before pairing; actual placement and hit testing remain unverified on Windows.
- The guarded native close event ignores the event and asks the app to coordinate it; App's main-window close and controller quit paths now use the coordinator, and `releaseAndTeardown()` returns false when the backend tracks a process or pending launch. The caller checks this result before unloading. These are source changes, not proof that all Qt, OS, Rust and external quit paths are guarded. The backend can deliberately remain in CLOSING indefinitely; retain the parent and host.

### Close coordinator and remaining Qt wiring

`CloseGate.qml` is an isolated coordinator for the proposed close gate, with an injected adapter contract; it does not itself intercept a window event, launch a process, perform Win32 calls, show a prompt or change the app. `test_close_gate.py` runs it with a fake QML adapter and tests synchronous/asynchronous close, duplicate requests, cancellation and exit races, polling, adapter failures and reentrancy. The local sandbox used the same offscreen software-only test shims as `test_clean_view.py`. These tests do not exercise the real C backend or app lifecycle.

1. The source changes attempt to intercept the main native close event and `AppController.quitRequested`, before destroying/unloading the window or calling `Qt.quit()`. The experimental native event handler ignores `QEvent::Close` before emitting `closeRequested`; `releaseAndTeardown()` checks tracking and the app respects its return value. These paths and all other shutdown paths still require full-app review and testing. The controller must outlive its process handle and parent HWND.
2. The coordinator retains the first requested action (tray versus quit), disallows duplicate requests and polls until its adapter confirms that the tracked process has exited. Its approval signal is wired to the corresponding teardown/quit path; all callers still need auditing and real tests. The adapter must never return `true` on an unknown or failed wait. Prevent starting the cleaner or unloading the controller while waiting. If no trusted attached child can be closed, instruct the user to close the cleaner themselves; do not terminate a process or target an unverified HWND.
3. Offer **Keep Sa6i Link open** if it takes too long or sending WM_CLOSE fails. The coordinator retains this intent even if cancellation initially fails or the cleaner exits concurrently. `embed_cancel_close()` attempts to return to the previous discovery/attached/unattached state without releasing the tracked process, but cannot revoke an already-posted WM_CLOSE. The cleaner might still exit afterward; the native adapter must continue polling independently after the close coordinator stops its timer, and explain the possibility to the user. Failed or unverifiable process waits must remain pending. After cancellation, a new close attempt can retry sending WM_CLOSE. If cancellation sees an already completed close, the adapter must reinitialize a fresh host only after confirmed exit, before a future cleaner launch.
4. An OS shutdown, crash, forced process termination or unexpected native-window destruction can bypass the gate; this proposal does not solve those cases. Review and test those separately. Do not claim a detached child is safely contained or that cancel undoes a close message.

- The sandbox's PySide6 runtime provides QML for isolated tests but no Qt C++ development headers or `moc`; a Windows PySide wheel inspected likewise contains bindings, not a Qt C++ SDK. A locally built Linux QtCore and moc now permit adapter tests, but there is still no verified matching-source Windows application build, and neither the adapter nor a modified app has been compiled or run on Windows.

## Boundary and layout

- Keep the existing `NativeWindow` as the single top-level app window. Provide a separate Sa6i Clean navigation entry and a content region inside it; switching back must restore the existing page, without changing the pairing state or relying on `AppController.currentPage` accepting a new page name.
- Decide explicitly whether the entry is available before pairing. In the checkout, `MainWindow.qml` hides both navigation rail and page loader during the welcome/walkthrough state; the welcome loader overlays the entire window. A working button must be intentionally placed in both states if it is to be accessible before pairing, without obscuring pairing controls or caption buttons. Do not add a fake cleaner page.
- A Windows-only C++ component should own the child process, native window and timer; QML exposes only activation and status. The component needs a correctly positioned native HWND region, not just a QQuickItem visual: native child windows do not participate in Qt Quick's normal z-order, clipping, animations or transparency. Never assume a QQuickItem is an HWND.
- Map the selected content area's coordinates from QML scene space to the parent HWND client coordinates in physical pixels. Recompute on geometry, visibility, window recreation and per-monitor DPI changes. Check both Qt and Electron DPI awareness settings. Guard against painting over the navigation rail, pairing UI and caption controls. Prove focus/tab/keyboard, mouse, minimize, maximize, restore and movement between monitors. Avoid page-transition transforms on native children.
- Establish creation and teardown ordering. `NativeWindow::releaseAndTeardown` explicitly destroys the HWND on close-to-tray; an embedded child must be handled before parent destruction, and recreated/reattached safely on restore. Test regular close, tray close, quitting, cleaner exit and app crashes. No unmanaged independent process or invisible stuck window.

## Launch and safety

- Use a separately installed, pinned **restricted** cleaner for initial integration tests. Verify the intended executable and ASAR; preserve upstream notices and GPL requirements. File hash checks can avoid accidental mismatches but are not authentication against a local attacker or a race. Do not quietly fall back to unrestricted cleaners.
- Track the launched process until confirmed exit. After timeout, failed attachment or loss of the HWND, do not discard ownership and relaunch; report a recoverable state. Never close or terminate a window merely because its title matches. A PID alone is insufficient against stale handles/PID reuse. `host_lifecycle.c` is an isolated state model, not an implementation of these requirements.
- Start the cleaner with normal user privileges. Handle elevation/integrity mismatch as a clear error, not by silently elevating. The experimental Qt backend now uses direct CreateProcessW and a fresh temporary profile argument, but this is not a sandbox. The earlier standalone host probe did not use this profile mechanism. Confirm actual Electron data location and independent single-instance behavior, and review other global paths, shell/registry operations, environment and crash handling on disposable Windows installations.
- Header adjustment and VxKex were needed for the user's experiment, but are not a general compatibility fix. Do not patch their installed software or VxKex configuration automatically. Missing API support, Electron subprocesses and the actual Sa6i Link executable require independent validation.

## Profile investigation

Static inspection of the exact restricted main bundle found `getPath("userData")` used for settings and keys, and `requestSingleInstanceLock()` called at startup; it also found separate uses of environment paths and the user's home directories. The executable contains the Electron version string `45.1.0`. In Electron's v45.1.0 source, [`PreSandboxStartup`](https://github.com/electron/electron/blob/v45.1.0/shell/app/electron_main_delegate.cc) overrides `DIR_USER_DATA` from `--user-data-dir` before application startup, and the [single-instance code](https://github.com/electron/electron/blob/v45.1.0/shell/browser/api/electron_api_app.cc) uses the user-data path. This supports the approach, but binary version inference and static source review do not prove the exact executable's runtime behavior. Check the actual settings location, cache, concurrent lock behavior and paths accessed on disposable Windows before relying on it.

The fake Win32 tests exercise distinct directory creation, collisions, access denial, malformed paths, quoting with spaces, and retention after a failed launch. They do not create a real directory, invoke CreateProcessW or launch Electron. No existing profile is intentionally deleted or migrated by this code. Testers should not blindly delete matching temp folders; review ownership and contents after all associated processes exit.

## Update and shutdown audit finding

The normal Windows updater's `install_with_task` starts its relauncher and the machine-wide `Nectarlink Update` scheduled task **before** calling `request_quit()`. The QML quit coordinator alone cannot undo an installer task already started. The prompt-based update path can start an installer directly.

The source now uses the **same build-time Windows opt-in** for a Rust `sa6i_clean_experiment` cfg and the C++ host flag. Under that cfg, `can_update` is false, update discovery/checks and channel writes are suppressed, staging and installation fail before IO, task/prompt entry points fail before spawning, and the update service fails before logging or network access. `main` also rejects setup, removal, uninstall, update service/relaunch, vcam registration and widget-provider modes; except for `--version`, it requires an explicit absolute `--data-dir`. Normal builds retain their updater behavior. An absolute path is not necessarily a new or safe directory; the tester must select an unrelated disposable one. These guards have not been validated by a full Cargo build or by executing the Windows app, and do not stop independently scheduled tasks, a separate installer, other binaries or unrelated OS integration. Other startup services still run. Do not test against a real installation or registered update task and do not change existing tasks. An isolated VM with backups and no existing installation remains required.

`test_experiment_guards.py` checks source ordering and the shared build decision structurally; `test_experiment_policy_rust.py` compiles the actual options validator with stubbed fields when `SA6I_TEST_RUSTC` is supplied. `test_updater_guard_rust.py` compiles selected actual updater functions with stubbed I/O under both ordinary and experimental cfgs. These passed locally using a third-party Rust 1.92 nightly toolchain, which is below the checkout's Rust 1.97 minimum and was used only for these isolated harnesses and parsing, not the full app. Rust unit tests for the parser and updater guards were added to the app but not run. None of these tests proves update side effects are blocked in a real compiled Windows build.

## Shared Windows integration audit

A separate data directory is insufficient for several host integrations. Windows toast startup writes the shared AUMID registry entry and clears that ID's notification history; Jump List registration writes links under the same shared ID. Windows phone-storage reconciliation can register/unregister shared sync-root IDs and delete placeholders outside the test data directory. The experimental build now short-circuits Windows toast process ID/start/unregister, Jump List register/unregister, storage start/sync/event/unregister, and global hotkey update/registration entry points. In particular, suppressing storage startup alone is not enough: a `DeviceRemoved` event can independently unregister a root. Hotkeys are guarded both at preference update and at tray-window creation, which calls registration directly. `test_hotkey_guard_rust.py` compiles the actual hotkey functions in ordinary and experimental modes with fake Windows APIs; it does not exercise real Win32 or the full application. The other guard tests inspect ordering in source but do not run these Win32 paths. The test build consequently does not support these integrations; its hotkey preference UI may still appear editable, but global hotkeys will not be registered. Networking (including BLE advertising), clipboard monitoring, other services and OS access remain active or unaudited; this is still **not isolation**. These guards require full Windows compilation and disposable-machine verification before a test package is distributed.

## Delivery gate

The published executable does not match a verified reproducible source build. Its extracted QML does not contain a host implementation, and editing the QML resource cannot alone add Win32 methods to `NativeWindow`. Before packaging, establish a reproducible compatible build or develop another reviewed way to add a native host; explicitly distinguish it from the tested release. Keep the original ZIP untouched and use a separately named package with isolated test data. A new application manifest, updates, file associations, protocol handlers and tray/single-instance behavior must be reviewed before any test near an existing install.

No release until destructive operations, junction and path handling, privacy, license notices, isolation and failure cases are reviewed and tested on disposable data with backups. The existing restricted experiment is not a complete sandbox or security audit.
